# Phase 05L — AquariumDive freeze diagnosis and correction

**MID-SCROLL FREEZE RESOLVED in the verified Windows Chrome configuration.** Completed only Phase 05L. Production changes are limited to `src/App.jsx` and `src/components/AquariumDivePrototype.jsx`. No deployment was performed.

1. **Exact reproduction.** Built the existing working tree before editing and used its production preview at `http://127.0.0.1:4173/`. In Windows Google Chrome 155.0.8059.40, 1440×900, Normal, dark, entered the portfolio after the loading gate. CDP native continuous mouse scrolling moved from scroll target P0 to P0.88 at 700 CSS px/s, settled 700 ms, then reversed without reload. Repeated three forward/reverse pairs. Controlled scrubs used native `scrollTo` updates over 6.5 seconds in each direction, two pairs. The cold baseline used a new Chrome profile and cleared HTTP cache; later repeated passes used the same document. Mobile comparison used 390×844 emulation. A separate production baseline for later A/B checks was rebuilt from the two byte-preserved pre-fix source snapshots, using identical public assets, served on 4176; working source was never reverted. Harness: [profile.mjs](profile.mjs), [browser.mjs](browser.mjs), [preserved-baseline builder](build-baseline.mjs).

2. **Measured progress.** Correlated camera XYZ against 2,001 samples of the actual existing camera path, including portrait adjustment, rather than treating scroll target as the displayed camera. Front is P0, elevated P0.30 is camera `[0,4.5,9.5]`, and downward P0.55 is `[0,8.5,9.5]`. The repeatable slowdown covered actual displayed P≈0.10–0.60. The large first-use freeze was at the existing P0.62 dissolve boundary: the cold trace spans displayed P0.6165→0.622 while the scroll target was ≈0.6767. The comparison range below explicitly includes P0.10–0.65. The attachment contained the brief but no accessible screenshot image files, so these state mappings use captured scene composition and instrumented camera positions, not a claimed pixel match to the user's screenshots.

3. **One-time versus repeated behavior.** Two separate problems were reproduced. First crossing introduced a 5,738.4 ms rAF gap and a 5,735.5 ms main-thread task. Its size decreased with shader-cache warming but remained 299.2 ms in the later untraced baseline. Reverse and subsequent natural passes retained roughly 26 ms median intervals, even though they performed no new shader compilation, texture upload, or render-target allocation. Thus repeated lag was not merely an initial loading issue. Controlled scrolling was less severe than natural scrolling; it still incurred excessive style work. Intentional camera lag was preserved and distinguished from missing frames.

4. **Root causes.** Repeated lag came from seven inherited atmosphere/bubble CSS custom properties on `.aqua-root` changing with `progress.t` throughout the intro, when the effects using them were invisible. These inline style mutations repeatedly invalidated roughly 584 descendant elements. The one-time freeze came from lazy initialization of the unchanged Normal-mode dissolve pipeline at P0.62: 21 additional desktop shader programs, two render targets, framebuffer/multisample storage, and synchronous first-use shader/program checks. Camera interpolation, cherry geometry and steady-state transparent rendering were not the measured primary causes.

5. **Diagnostic and isolation evidence.** CDP traces show React inline CSS mutations on `.aqua-root` and long `UpdateLayoutTree` work. Warm natural baseline passes spent about 2.0–2.1 seconds recalculating style; forced layout duration was essentially zero. A temporary browser-only A/B held just the seven hidden CSS values and preserved the full WebGL scene: reverse-pass style work fell from 2,242.1 to 212.9 ms; median intervals fell from 25.7 to 13.3 ms. A production build with only the App fix independently reproduced the gain (reverse style 218.2 ms, median 13.3 ms), while its first crossing still stalled 310.8 ms and linked 21 programs. Adding the measured preparation fix removed that remaining initialization at the crossing. The cold baseline trace's large task contains GPU program waits; later API instrumentation directly identifies blocking `getProgramInfoLog` calls. Initial programs now reach 45 before entry versus 24 before; desktop and mobile final scrolling triggered zero new shader links, framebuffers, model buffer uploads or texture uploads. [Baseline analysis](baseline/analysis.json), [isolation](isolation/analysis.json), [CSS-only stage](css-only/analysis.json), [final desktop](after-full/analysis.json).

6. **Exact code changes and their limits.** In `App.jsx`, compute the existing `visualEntered` first, then hold `bubbleDepth` at zero until that visibility condition. All seven original formulas resume their original values in the same render in which the effects become visible. In `AquariumDivePrototype.jsx`, reuse `ensureTransition`, await existing asset-placement promises, initialize its existing render targets, and compile its world/quad shader variants with installed Three.js `compileAsync`. Track this in the existing readiness gate. Temporarily suppress Dive drawing while compilation is pending so ordinary rendering cannot replace Three.js's program reference during readiness polling; simulation and camera code remain unchanged. Perform one warm-up of the existing compositor, restore the actual current view, and memoize preparation on that transition resource. Normal-mode restoration prepares a newly recreated transition too; Lite, Reduced Motion and backdrop-only paths skip this preparation. Existing renderer/context, targets, resize and disposal mechanisms are reused. No permanent loop, dependency, source comment, quality reduction, camera/easing/lag change or asset change was added. Tradeoff: preparation and render-target residency move earlier into loading; work is moved, not removed. The separate fresh-profile run observed ready P0 at 12.95 seconds from navigation, including existing startup, entry/fade and probe setup. Cold startup still has shader/asset long tasks behind the loader; this phase does not claim to eliminate startup cost.

8. **Main thread and GPU.** The repeatable cost was style recalculation, not geometric reflow: warm layout duration stayed near zero. React commits continued and increased in count as frame cadence improved; no claim of eliminating React renders is made. Total JavaScript per pass can increase because approximately twice as many frames are rendered. GC was observed (cold baseline major GC up to 16.8 ms) but did not explain the multi-second stall. Final desktop trace main tasks peaked at 28.0 ms; mobile 36.0 ms; final desktop GC peak was 4.6 ms. Hardware WebGL used ANGLE/NVIDIA GeForce RTX 2060/D3D11. `EXT_disjoint_timer_query_webgl2` was supported and disjoint results were discarded. In the elevated front-facing subset, desktop GPU render query medians stayed comparable: roughly 8.4/9.5 ms control forward/reverse, 8.0/8.3 ms with only hidden variables held, and 8.1/8.2 ms final first forward/reverse. These queries measure renderer command spans, not full browser presentation; no universal GPU headroom claim is made. Unchanged main-scene P0/P0.5 workload is 119 draws and 331,291 submitted triangles, with six tree main-pass draws/1,944 triangles. Transparent main-pass callbacks remained 31 before the dissolve. Glass/water use existing transparent materials; no new refraction pass or transmission setting was introduced. Camera coverage can still affect GPU cost on other hardware, but isolation does not support it as this repeatable freeze's primary cause. One Dive context remained active throughout each measured intro, with zero losses; no new application animation loop was added. Existing shared scroll scheduler, fish loop and GSAP behavior are retained; handoff/hidden-tab tests confirm renderer draw ownership and pausing.

13. **Remaining uncertainty and preservation.** Headless Chrome with hardware WebGL is not the user's interactive browser session; refresh cadence, drivers, thermal state and other workloads may differ. Separate fresh Chrome profiles and cleared HTTP cache were used, but OS/driver shader caches cannot be proven flushed. The structural result is independent of that uncertainty: no first-use program/target work occurs during the final measured crossing, even after a new browser profile. Trace/instrumentation overhead exists; untraced controls support the same result. Before/after GPU query figures are samples, not whole-machine GPU utilization. No physical-phone result or exact screenshot-reference match is claimed. Startup work is explicitly retained under loading. Preservation verification checked **2585** pre-existing files: only the two authorized source files differ; no pre-existing file is missing, and all others—including previous uncommitted/untracked Phase 05K artifacts and both cherry GLBs—have identical bytes. No forest/fish/terrain asset, dependency, CSS file, camera key or carousel file was modified. 14. **Recommended next optimization.** None is justified for this freeze after these measurements. Verify the same journey in the user's interactive Chrome and on physical mobile hardware before considering another performance change. Cold startup latency is a separately measurable candidate if the loading duration is unacceptable; do not change approved rendering quality or begin another phase automatically.

15. **Final verdict: MID-SCROLL FREEZE RESOLVED.** The actual elevated/downward camera range and first-use dissolve boundary were verified after both accepted fixes, across cold entry, repeated natural forward/reverse movement and controlled scrubs. This verdict applies to the tested Chrome configuration; the unrelated existing Projects timing failure and hardware-testing limitations remain explicitly recorded. Stopped after Phase 05L.
